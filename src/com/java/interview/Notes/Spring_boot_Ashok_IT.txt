What is Component Scanning?
-----------------------------
-> Programmer has to enable component scanning in spring framework

-> Programmer no need to enable component scanning in spring boot (by default it is enabled as part of Start class)
------------------------------------------------------------------------
-> Component Scanning is the process which is used to identify component classes (spring beans) available in the application.

-> Component Scanninng will work based on base package naming convention

---------------------------------------------------------------------------------------------------------------------------------------------------------

-> Component Scanning is the process of identifying spring bean classes available in the application.

-> In Spring Boot, Component Scanning is enabled by default.

-> In Spring Boot, Component Scanning will start from base package.

Note: The package which contains start class is called as base package.

-> Once Base package scanning is completed, it will search for sub packages of base package and will scan them.

Note: The packages which are starting with base package name are called as Sub packages of base package.

		in.ashokit  -----------------> Base package

		in.ashokit.beans ------> It is sub package for base pkg

		in.ashokit.dao -------> It is sub package for base pkg

		in.ashokit.service ------> It is sub pkg for base pkg

		in.ashokit.controller-----> It is sub pkg for base pkg

		in.ashokit.util-------> It is sub pkg for base pkg

		in.ashokit.service.admin-----> It is sub pkg for base pkg

		com.ashokit.model ----------> Not a sub package

-> If we have multiple packages with different names then we have to specify @ComponentScan annotation like below

		ConfigurableApplicationContext ctxt = SpringApplication.run(Application.class, args);
	}

-> In Realtime we will develop our applications using Layered Architecture

		-> Presentation Layer (Ui)

		-> Web Layer (Controller Classes)

		-> Business Layer (Service classes)

		-> Persistence Layer (Dao/Repository classes)


-> User Interface Logic will be available in Presentation Layer

-> Web layer contains Controller classes which are responsible to handle request and response in web application.

-> Business Layer Contains Service classes which are responsible to execute business logic

  Ex: Sendng Email, Password Encryption & Decryption, Report Generation etc.

-> Persistence Layer Contains Dao/Repository classes which are responsible to communicate with database.
--------------------------------------------------------------------------------

-> Controller class method should call service class method so Service Class Object should be injected into controller class object.

-> Service class method should call dao method so dao class object should be injected into service class object.

-> To inject one class object into another class object we will use @Autowired annotation

-> The process of injecting one class object into another class object is called as  ' Dependency Injection '.

-> In Spring / Spring Boot IOC container is responsible to perform this Dependency Injection.

-> @Autowired annotation we can use at below 3 places

		1) At Constructor Level (Constructor Injection)

		2) At Setter Level (Setter Injection)

		3) At Field Level (Field Injection)

-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
-> The process of injecting dependent bean object into target bean object through target bean constructor is called as 'Constructor Injection'.

-> To peform Constructor Injection, IOC will create Dependent Bean object first then it will create Target Bean object.

-> To inform IOC to perform Constructor Injection we will write @Autowired annotation at target class constructor.

Note: If target class is having only one parameterized constructor then writing @Autowired is optional.

----------------------------------------------------------------------------------
@Service
public class UserService {

	private UserDao userDao;

	@Autowired
	public UserService(UserDao userDao) {
		System.out.println("UserService :: 1-Param Constructor");
		this.userDao = userDao;
	}
}

package in.ashokit.service;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

import in.ashokit.dao.UserDao;
import in.ashokit.util.EmailUtils;
import in.ashokit.util.PwdUtils;

@Service
public class UserService {

	private PwdUtils pwdUtils;

	private EmailUtils emailUtils;

	private UserDao userDao;

	public UserService() {
		System.out.println("UserService::Constructor");
	}

	@Autowired
	public void setPwdUtils(PwdUtils pwdUtils) {
		this.pwdUtils = pwdUtils;
	}

	@Autowired
	public void setEmailUtils(EmailUtils emailUtils) {
		this.emailUtils = emailUtils;
	}

	@Autowired
	public void setUserDao(UserDao userDao) {
		this.userDao = userDao;
	}

	public void registerUser() {
		pwdUtils.encryptPwd();
		userDao.save();
		emailUtils.sendEmail();
		System.out.println("User Record Saved....");
	}

}

ANSWERS
Answering these questions comprehensively will demonstrate a deep understanding of microservices configuration. Here are sample answers to guide your responses:
 
1. Service Discovery and Load Balancing
•	Service Discovery Configuration:
o	In microservices, service discovery helps dynamically locate services as they scale or change. With client-side discovery (e.g., Ribbon in Spring Cloud), the client knows about all service instances and chooses one for each request. This is suitable for smaller deployments with simpler load-balancing logic. Server-side discovery (e.g., Netflix Eureka, Consul) offloads service selection to a central server, which is often better for large systems where the discovery server can manage and distribute load.
•	Load Balancer and API Gateway:
o	An API Gateway (e.g., Spring Cloud Gateway, Kong, or Zuul) can manage routing and load balancing for requests entering the system. Configuration typically involves setting route mappings, rate limits, and timeouts, enabling the gateway to distribute incoming requests across services and provide a single entry point for clients.
2. Configuration Management
•	Environment-specific Configurations:
o	Use a configuration server, like Spring Cloud Config, to manage settings for different environments (dev, staging, prod). You can store configurations in Git and have the server retrieve the right configurations based on the environment.
•	Securing Sensitive Information:
o	Use tools like HashiCorp Vault, AWS Secrets Manager, or Spring Cloud Vault to store sensitive configurations. Encrypt configurations, and access them through APIs rather than hardcoding in config files.
•	Spring Cloud Config Setup:
o	Spring Cloud Config can pull configurations from a Git repository. To set it up, define application profiles and branch mappings in the application.yml, pointing to different Git paths or branches for each environment.
3. Inter-Service Communication and Resilience
•	Circuit Breaker Pattern:
o	Implement circuit breakers (e.g., Resilience4j or Hystrix) to prevent failures from cascading across services. A circuit breaker can be configured to open after a set number of failures, pause for a timeout, and then retry, allowing degraded service without overwhelming dependent services.
•	Retry Mechanism:
o	Use retry policies in Resilience4j or Spring Retry. Configure exponential backoff in the retry settings to avoid network congestion by spacing out retries in case of repeated failures.
•	Synchronous vs. Asynchronous Communication:
o	REST (synchronous) is straightforward but can cause blocking if the dependent service is slow. Asynchronous communication (e.g., via Kafka or RabbitMQ) allows non-blocking calls, ideal for events where response time isn’t critical. Configure Kafka consumers in Spring Boot with listeners and ensure idempotency for retries.
4. Logging and Monitoring
•	Centralized Logging:
o	Use ELK stack (Elasticsearch, Logstash, Kibana) or similar tools to aggregate logs. Use Correlation IDs (with Spring Sleuth) for tracing requests across services, configuring log levels and filters in the application.yml file for consistent log formatting.
•	Monitoring with Prometheus and Grafana:
o	Configure Prometheus to scrape service metrics (e.g., CPU, memory usage) and visualize with Grafana. Spring Boot Actuator can expose these metrics, allowing alerts for critical events, like memory or response time thresholds.
5. Security and Authentication
•	OAuth2 and JWT:
o	Set up an authentication server with OAuth2 to issue JWT tokens. Configure resource servers to validate JWT tokens using filters in Spring Security. Each service can validate tokens without needing the auth server for every request.
•	Shared Authentication (Single Sign-On):
o	Use a centralized auth provider like Keycloak, Okta, or Auth0. Configure microservices to delegate authentication, using a shared JWT or SSO token across services for identity propagation.
•	Mutual TLS:
o	Configure each service with its own TLS certificate and configure mutual TLS on API gateways and load balancers. This ensures services only communicate over encrypted channels.
6. Database and Data Consistency
•	Distributed Transactions:
o	Use the Saga pattern, managing each step of a transaction in different services and coordinating with compensating actions for failure. Spring Boot has libraries that support distributed transactions (e.g., Axon Framework).
•	Eventual Consistency:
o	Implement eventual consistency with message brokers like Kafka. Services publish events for others to subscribe, reducing the need for transactions across services. Configure Kafka for at-least-once delivery and idempotency in listeners.
•	Schema Changes:
o	Use database migration tools (e.g., Flyway or Liquibase) to handle schema changes incrementally. Each service manages its schema and uses API versioning for backward compatibility.
7. Event-Driven Microservices
•	Event-Based Communication:
o	Set up Kafka with topics for each event type. Configure consumer groups in Spring Boot to allow scaling without duplicate processing. Use topics and partitions wisely to balance load.
•	Message Serialization:
o	Use a format like Avro or Protobuf for compact, schema-based serialization. This ensures consistency across services and backward compatibility by supporting schema evolution.
•	Event Sourcing:
o	Log each event that changes state to an event store (e.g., Kafka or a dedicated event log). This approach enables an audit trail, and services can replay events to reconstruct past states.
8. Deployment and Scaling
•	Blue-Green/Canary Deployments:
o	Blue-green deployments run two environments (old and new versions) simultaneously, allowing traffic to be directed to the new one once tested. Canary releases, achieved with weighted load balancing, roll out changes incrementally.
•	Autoscaling in Kubernetes:
o	Configure Horizontal Pod Autoscaler (HPA) based on CPU, memory, or custom metrics. Set minimum and maximum pod limits in your deployment YAML.
•	Rolling Updates in Kubernetes:
o	Set rolling update strategy in the deployment YAML, defining maxSurge and maxUnavailable to control the pace of the update and ensure minimal downtime.
9. Resiliency and Fault Tolerance
•	Distributed Tracing:
o	Use Spring Cloud Sleuth and Zipkin to trace requests across services. Sleuth attaches trace IDs and span IDs to logs, which Zipkin collects to visualize request flows and identify slow components.
•	Service Mesh:
o	With Istio, set retry policies, circuit breakers, and traffic routing rules. You can use Istio’s fault injection feature to test resilience by introducing artificial delays or errors.
10. API Gateway Configuration
•	Routing and Rate Limiting:
o	Spring Cloud Gateway allows configuration of routes based on URL patterns, with filters for rate limiting and authentication. Define rate limits and set up custom filters in the application.yml.
•	Fallback Configuration:
o	Set up fallback routes to handle degraded service gracefully. You can configure custom error pages or responses to provide meaningful feedback to users during outages.
11. Caching and Performance Optimization
•	Distributed Caching:
o	Use Redis for distributed caching to avoid hitting the database repeatedly. Configure Spring Boot to cache frequently requested data, setting cache expiration times to prevent stale data.
•	CDN for Static Assets:
o	Use a CDN like Cloudflare or AWS CloudFront to serve static content close to users. This reduces latency, offloading requests from your application servers.

1. Service Discovery with Eureka
Eureka allows for service registration and discovery in Spring Boot microservices.
Eureka Server Setup
Add the following dependencies to your pom.xml:
xml
Copy code
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-server</artifactId>
</dependency>
Create an @EnableEurekaServer-annotated Spring Boot application:
java
Copy code
@SpringBootApplication
@EnableEurekaServer
public class EurekaServerApplication {
    public static void main(String[] args) {
        SpringApplication.run(EurekaServerApplication.class, args);
    }
}
Configure the application.yml:
yaml
Copy code
server:
  port: 8761
eureka:
  client:
    register-with-eureka: false
    fetch-registry: false

For services that need to register with Eureka, add the following dependency:
xml
Copy code
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
</dependency>

java
Copy code

3. Resilience with Circuit Breakers (Resilience4j)
Add Resilience4j to pom.xml:
xml
Copy code
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot2</artifactId>
    <version>1.7.1</version>
</dependency>
Configure resilience properties in application.yml:
yaml
Copy code
resilience4j:
  circuitbreaker:
    instances:
      myService:
        slidingWindowSize: 10
        failureRateThreshold: 50
        waitDurationInOpenState: 10000 # in ms
Implement in your service class:
java
Copy code
@RestController
public class MyController {
    
    @Autowired
    private MyService myService;

    @GetMapping("/process")
    @CircuitBreaker(name = "myService", fallbackMethod = "fallback")
    public String process() {
        return myService.process();
    }

    public String fallback(Throwable t) {
        return "Fallback response";
    }
}
