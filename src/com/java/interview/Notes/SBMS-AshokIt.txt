What is Monolith Architecture?
---------------------------------------------------------------------------------
-> If we develop all the functionalities in one single application then we will call it as Monolith Architecture based application.
-> When we package our application we will get one war file.
-> Monolith application war files are called as fat war files or heavy weight war files
-> It is very difficult to manage and maintain fat war files
Advantages
----------
1) Implementation will be easy
2) Bug Tracking/Debugging Will be easy
3) Better throughput
Dis-Advantages
---------------
1) Tighthly coupling among the components
2) Less Scalability
3) Burden on server
4) Deployment process will be difficult
5) Load Balancing is difficult & challenging
----------------------------------------------------------------------------------
-> To avoid the problems of Monolith Architecture, Microservices Architecture Came into picture.
----------------------------------------------------------------------------------
What is Microservices ?
----------------------------------------------------------------------------------
-> Microservices is not a programming language
-> Microservices is not a technology
-> Microservices is not a framework
-> Microservices is not an API
-> Microservices is a design pattern which is used to develop our application functionalities with loosely coupling.
-> Microservices architecture is not specific to any technology.
---------------------------------------------------------------------------
Features of MicroServices
-----------------------------------------------------------------------------------
1.Decoupling
  Services are largely decoupled the application as a whole can therefore be easily constructed altered and scalable
2.compenentization:you can view as a independent component that can easily be exchanged or upgraded
3.Business capability:Only focus on one service
4.Autonomy:Each developer focus on independent services
5.continuous delivery

                                                Service Registry
                                                      ^   |
                                           (2 request)|   v(3 response)
client--DNS-- api/order(1 request)------->Region1-->API Gateway--(4 request)--->A1 Zone -->Load balancer---->order(microservice- it having multiple instances)

client<---DNS- api/order(6 response)<-------Region1API Gateway<----region 1<-----A1 zone<-----Load balancer<--(5 response)-order(microservice- it having multiple instances)

Steps of the Request Flow
Client Request via DNS:

The client initiates a request to api/order, using a DNS service to locate the API endpoint. This could be a public domain or IP address that routes the request to the appropriate API Gateway.
API Gateway Handling:

The request reaches Region1 API Gateway, which acts as a central point for routing and managing requests to different microservices, such as order in this case.
The API Gateway may perform authentication, authorization, and rate limiting as well.
Service Discovery and Routing to Load Balancer:

The API Gateway consults the Service Registry to locate instances of the order service available in Region1.
Once located, the API Gateway forwards the request to the appropriate Load Balancer in Zone A1, which balances requests across the multiple instances of the order microservice.
Load Balancer Forwarding to Order Service:

The Load Balancer in Zone A1 receives the request and routes it to one of the instances of the order microservice. This helps distribute traffic evenly, optimizing for availability and scalability.
Order Microservice Processing:

The instance of the order microservice processes the request and returns a response back to the Load Balancer.
Response Flow Back to the Client:

The Load Balancer returns the response to the API Gateway in Region1.
The API Gateway then sends the response back through DNS to the client, completing the full round trip.

Today's session : Load Balancing
---------------------------------------------------------------------------------
-> Load Balancing is the process of distributing load from one server to multiple servers.
-> If we deploy our application in one server then it is responsible to handle all incoming requests.
-> If all requests are going to single server then burden will increase on the server.
-> If burden increased on server then we will see below issues
		1) Response Delay
		2) Server Crash etc..
-> To avoid these problems we will deploy our application using Load Balancer.
-> Load Balancing we can implement in 2 ways
		1) Server Side Load Balancing
		2) Client Side Load Balancing
-------------------------------------------------------------------------------------------------------------------
-> To implement Server Side balancing Load Balancer algorithm will be configured to decide which request should be processed by which server.
			i) Round Robbin(Trending)
			ii) Sticky Session
			iii) Ip Hashing
Q) What is scale up?
Q) What is scale down?
-> Adding more servers to LBR based on demand is called as Scale up.
-> Removing servers from LBR is called as Scaled down.
-> Adding servers and removing servers manually is time taking process.
-> Now a days we are using Auto-Scaling.
Q) What is Auto Scaling?
-> It is the process of adding and removing servers from LBR based on demand.
Ex: Amazon BigDay sale, Flipkart BigDay Sale etc..
-> Companies can't guess traffic on Big Day sale that's why they will prefer AutoScaling.

Today's session : Apache Kafka
--------------------------------------------------------------------------------
-> Distributed systems are collection of computers that work together to form single computer for end users.
-> Distributed systems can handle billions of requests and upgrades without downtime.
-> Apache Kafka has become one of the most widely used Distributed Systems on the market today.
-------------------------------------------------------------------------------
-> Apache Kafka is an open-source distributed event streaming platform used by thousands of companies for high-performance and data pipelines, streaming analysis, data integration, and mission-critical applications.
-> Kafka is used by most fortune 100 companies like Linkedin, Netflix and Microsoft etc.
-> Apache Kafka is an open-source software which is written in Scala and Java programming languages.
-> Kafka started in 2011 as a messaging system for Linkedin but has since grown to became a popular distributed event streaming platform.
-> Apache Kafka is capable of handling trillions of records per day.


Apache Kafka Use cases
----------------------
1) Processing financial transactions in realtime
2) Tracking and Monitoring Trasportation Vehicles in real-time
3) Capturing and Analyzing sensor data
4) Collecting and reacting to customer interaction
5) Monitoring hospital patients
6) To develop Event-Driven Microservices etc..
1. Producer Sends Data
Producer applications publish messages to a specific topic in Kafka. A topic is a logical channel or category through which data flows, like a stream.
Data is divided into partitions within a topic. Each partition is an ordered sequence, and data inside a partition is immutable.
Producers choose the partition to send data to, either randomly, round-robin, or based on a key (for ordering guarantees).
2. Kafka Broker Stores Data
Kafka brokers (servers in the Kafka cluster) receive data from producers. Each topic can be partitioned across multiple brokers.
The broker stores the messages durably, typically for a set retention period, allowing consumers to read at their own pace.
Each message is assigned an offset, a unique identifier within the partition, which allows consumers to track their read position.
3. Consumer Reads Data
Consumers subscribe to one or more topics to read data.
Each consumer reads messages from a specific partition and offset, keeping the order within the partition.
Consumers can control their read position by specifying an offset, enabling them to reprocess or skip data as needed.
4. Consumer Group Coordination
Consumer groups allow multiple consumers to share the load. Each consumer in a group reads from a unique set of partitions.
If a new consumer joins the group, Kafka rebalances partitions across consumers for optimal data processing.
5. Acknowledgments and Offsets
Consumers process messages and acknowledge them to Kafka, which allows for offset tracking and commits.
Offset management can be automatic (Kafka commits periodically) or manual (the consumer commits offsets when ready).

Last session : What is Cache & why we need to go for cache
------------------------------------------------------------------------

-> Cache is a temporary storage which is used to store & access the data frequently.
-> In our application we will deal with two types of tables
		1) Transactional tables
		2) Non-transactional tables
-> If application is performing insert/update/delete operations in the table then it is called as transactional table.
-> If application is performing only select(read) operation on the table then that table is called as non-transactional table.
-> The data which we have in non-transactional table is called as static data.
-> If we are using static data in our application then we can implement cache to improve performance of the application.
How to implement cache
----------------------
-> Once application got started take data from db and store that into cache in the form of key-value pair.
-> When application needs that data take it from cache memory instead of making db call.
-> By using cache memory we can reduce no.of db calls hence application performance will be improved.
Q) What is Local cache & What is distributed cache ?
-----------------------------------------------------
-> If we implement cache with in one application then it called as local cache.
-> If we want to use cache data in multiple applications then we should go for distributed cache (Ex: Redis cache)
Q) What is Redis?
------------------
-> Redis is an open source cache which is used to store the data in the form key-value pair.
-> Multiple applications can connect to Redis cache to access the data.

package com.tekleads.repository;

import java.util.Map;

import org.springframework.data.redis.core.HashOperations;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Repository;

import com.tekleads.model.User;

@Repository
public class UserRepositoryImpl implements UserRepository {

	private HashOperations<String, String, User> hashOperations;

	public UserRepositoryImpl(RedisTemplate<String, User> redisTemplate) {
		hashOperations = redisTemplate.opsForHash();
	}

	@Override
	public void save(User user) {
		hashOperations.put("USER", user.getId(), user);
	}

	@Override
	public Map<String, User> findAll() {
		return hashOperations.entries("USER");
	}

	@Override
	public User findById(String id) {
		User user = (User) hashOperations.get("USER", id);
		return user;
	}

	@Override
	public void update(User user) {
		save(user);
	}

	@Override
	public void delete(String id) {
		hashOperations.delete("USER", id);
	}
}

package com.tekleads.rest;

import java.util.Map;

import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import com.tekleads.model.User;
import com.tekleads.repository.UserRepository;

@RestController
@RequestMapping("/rest/user")
public class UserResource {

	private UserRepository userRepository;

	public UserResource(UserRepository userRepository) {
		this.userRepository = userRepository;
	}

	@PostMapping(value = "/add", consumes = "application/json")
	public User add(@RequestBody User user) {
		userRepository.save(user);
		return userRepository.findById(user.getId());
	}

	@PutMapping("/update/{id}/{name}")
	public User update(@PathVariable("id") final String id, @PathVariable("name") final String name) {
		userRepository.update(new User(id, name, 1000L));
		return userRepository.findById(id);
	}

	@DeleteMapping("/delete/{id}")
	public Map<String, User> delete(@PathVariable("id") final String id) {
		userRepository.delete(id);
		return all();
	}

	@GetMapping("/all")
	public Map<String, User> all() {
		Map<String, User> findAll = userRepository.findAll();

Q3: Explain SOLID Principle?

		Single Responsibility Principle (SRP): A class should have only one reason to change, meaning it should have a single responsibility or job.

		Open-Closed Principle (OCP): Software entities should be open for extension but closed for modification.

		Liskov Substitution Principle (LSP): Objects of a superclass should be able to be replaced with objects of its subclasses without breaking the behavior of the program.

		Interface Segregation Principle (ISP): Creation of smaller, more cohesive interfaces instead of large ones that cover multiple scenarios.

		Dependency Inversion Principle (DIP): This principle encourages the use of interfaces and dependency injection to decouple modules and make them more reusable and testable.

1. What is the Circuit Breaker Design Pattern?
The Circuit Breaker pattern acts as a proxy for the service call. It works in three states:

Closed: Requests go through normally.
Open: Requests are blocked for a configured duration after failures reach a threshold, preventing further calls to the failed service.
Half-Open: After a certain delay, the circuit breaker allows a few requests to check if the service is available again. If successful, it transitions to the Closed state; if not, it goes back to Open.
The Circuit Breaker pattern improves resilience by isolating failures and avoiding further load on the struggling service.

2. Steps to Create Circuit Breaker in Spring Boot Using Resilience4j
Add Dependency: Resilience4j is a popular library in the Spring ecosystem for implementing Circuit Breaker.

xml
Copy code
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot2</artifactId>
    <version>1.7.0</version>
</dependency>
Enable Circuit Breaker in the Application: Use the @EnableCircuitBreaker annotation in your Spring Boot main class.

Define Circuit Breaker Configuration: In application.yml or application.properties:

resilience4j.circuitbreaker:
  configs:
    default:
      failure-rate-threshold: 50
      wait-duration-in-open-state: 10000ms
      permitted-number-of-calls-in-half-open-state: 3
      sliding-window-size: 10
Wrap Service Calls with Circuit Breaker: Use the @CircuitBreaker annotation to wrap specific methods in a class:

@Service
public class MyService {

    @CircuitBreaker(name = "myService", fallbackMethod = "fallbackResponse")
    public String performAction() {
        // Call to external service
    }

    public String fallbackResponse(Exception ex) {
        return "Fallback response";
    }
}
Configure Fallback Method: Define a fallback method that returns an alternative response when the circuit is open. This is essential for a smooth user experience.

Monitor Circuit Breaker Metrics: Use Actuator endpoints or integrate with monitoring tools to observe circuit states.

3. Where to Use the Circuit Breaker Design Pattern?
Use this pattern when calling:

External APIs: Especially if they have high latency or may experience intermittent downtime.
Remote Microservices: To protect microservices from cascading failures in a distributed environment.
Network-Dependent Services: When services rely heavily on network requests, which can fail or timeout due to network issues.
4. Alternatives to Circuit Breaker Design Pattern
Retry Pattern: Retry the failed service a set number of times with a delay in between each try. Suitable when failures are intermittent.
Timeout Pattern: Set timeouts for external calls to avoid waiting indefinitely for a response.
Rate Limiting: Limit the number of requests to a particular service to prevent overload.
Bulkhead Pattern: Isolate services or modules to avoid a complete failure from spreading across the system.
5. Common Interview Questions on Circuit Breaker
What are the different states of a circuit breaker, and when does it transition between them?

Explanation: Discuss Closed, Open, and Half-Open states, and transitions based on failure thresholds and recovery checks.
How does the Circuit Breaker pattern improve fault tolerance in a microservices architecture?

Answer: By preventing cascading failures, isolating faults, and providing fallbacks, it allows services to recover without affecting the entire system.
How would you configure a circuit breaker for a service with a high failure rate but critical to the business?

Answer: Use a lower failure-rate threshold, shorter timeout duration, and quick retry interval.
What’s the difference between Circuit Breaker and Retry patterns?

Answer: The Retry pattern attempts to re-execute a failed call a few times before giving up. Circuit Breaker, on the other hand, blocks calls once a failure threshold is reached and allows retry only after a set timeout.
6. Scenario-Based Questions
Scenario: You have a payment microservice that occasionally fails due to network latency. How would you ensure it doesn’t affect the user experience on the checkout page?

Answer: Implement a Circuit Breaker to cut off calls after a certain threshold, providing a fallback method that either retries later or notifies users about the temporary unavailability.
Scenario: Suppose you’re dealing with a batch processing system where each service call takes around 5 seconds, but any delay beyond that affects SLAs. How would you handle failures in such a system?

Answer: Use both Circuit Breaker and Timeout patterns. Set a timeout for each call and allow the Circuit Breaker to open when timeouts are frequent, switching to a fallback response or retry mechanism to maintain SLA compliance.
Using the Circuit Breaker pattern strategically helps improve application robustness, especially in distributed environments.

15 How is spring security implemented in a spring boot application?
Implementing Spring Security in a Spring Boot application involves 3 steps — configuring security settings, authentication, and authorization.
Step-1 Adding Spring Security Dependency:
Include the Spring Security dependency in the project’s pom.xml (Maven) or build.gradle (Gradle) file. To get started with Spring Security, add the following dependency to your Spring Boot project’s build file (Maven or Gradle):

    <groupId>org.springframework.boot</groupId>

Note: After adding the above dependency, Spring Boot will automatically configure Spring Security with default settings.
Step-2 Creating Security Configuration
Create a security configuration class by extending WebSecurityConfigurerAdapter and override its configure method to define security rules, authentication, and authorization configurations.
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.annotation.web.configuration.WebSecurityConfigurerAdapter;

@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {


    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            .authorizeRequests()
                .antMatchers("/public/**").permitAll()
                .anyRequest().authenticated()
                .and()
            .formLogin()
                .loginPage("/login")
                .permitAll()
                .and()
            .logout()
                .logoutUrl("/logout")
                .permitAll();
    }
}
Step-3 Defining Authentication Providers:
Configure authentication by specifying user credentials or integrating with authentication providers like databases, LDAP, OAuth, etc., based on the application’s requirements.
Code Example (In-memory Authentication):
import org.springframework.context.annotation.Configuration;

@EnableWebSecurity

        auth
            .inMemoryAuthentication()

    }

23 What are coupling and cohesion?
Coupling and Cohesion are fundamental concepts in software architecture. Coupling refers to the degree of interdependence between software modules. For example, a lower coupling means that each component is independent and changes in one will not affect the others. On the other hand, Cohesion refers to how closely the responsibilities of a module or component are related to each other. For example, higher cohesion means that each module is responsible for a single task or function.
A well-designed application should aim for low coupling and high cohesion. Low coupling ensures that each service operates independently, minimizing the knowledge they need about each other. This independence makes the system more robust and easier to maintain. High cohesion means that all the related logic is kept within a single service, preventing unnecessary communication between services which could impact performance.
